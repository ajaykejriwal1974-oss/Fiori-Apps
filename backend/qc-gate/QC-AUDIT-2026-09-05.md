## 2. Backend findings

### 2.1 ZBP_I_QC_INSP_LOT — three actions declared, none implemented (severity: high)

`ZI_QC_INSP_LOT` declares six actions (WBCROSSGT confirms the projection uses
`RELEASETOPRODUCTION`, `CONFIRMDYEING`, `CONFIRMWINDING`), but the active
local implementation of the behaviour pool implements only
`recordSingleResult`, `recordResults`, `setUsageDecision`. The 28-Aug
additions (`locals-additions.abap`) were drafted and never pasted. Pressing
Release to Production / Confirm Dyeing / Confirm Winding therefore
short-dumps ("no handler for action"), and because instance feature control
never set those flags, `__OperationControl` reported them as enabled.

Fix: `zbp_i_qc_insp_lot.clas.locals_imp.abap` in this folder is the COMPLETE
local-types include — the live code plus the three handlers, the validation
helper, `read_ud`, extended feature control (each follow-on only for its own
inspection type, only after an accepting usage decision on QAVE) and the two
saver blocks (301 transfer via `BAPI_GOODSMVT_CREATE`, confirmations via
`BAPI_PRODORDCONF_CREATE_TT` + `ZQC_CONF_BATCH`). One correction against the
draft: `BAPI_PP_TIMETICKET` has no `CONF_CNT`; the counter is taken from
`DETAIL_RETURN` (`BAPI_CORU_RETURN-CONF_CNT`, verified in DD03L).

**Paste it** in Eclipse: ZBP_I_QC_INSP_LOT → *Local Types* tab → replace all →
activate, recording the class on KSDK906908. The ADT bridge can read but not
write class-local includes.

### 2.2 ZBP_I_QM_INSPECTIONCHAR — results were never written (severity: high)

`save( )` called `BAPI_INSPCHAR_SETRESULT DESTINATION 'NONE'` and never
committed that session, so no result ever reached QAMR; the BAPI RETURN was
ignored; `update( )` CLEARed the buffer on entry, so a multi-row $batch kept
only its last row. The app said "n result(s) posted" throughout.

Fix: `zbp_i_qm_inspectionchar.clas.locals_imp.abap` — commit/rollback in the
same RFC session, every RETURN passed back through `reported`, buffer keyed
and cleared only after save/cleanup, and a new check that the lot has no
usage decision yet. **Paste it** the same way.

### 2.3 ZI_QM_INSPECTIONCHAR — no "open" filter (severity: medium) — DONE in KSD

The view returned every characteristic of every lot ever created (206 rows
in KSD, all history). Now `where lot.stat35 = ''` and the QAMR record not
closed (`satzstatus <> '5'`), via an explicit left outer join → 103 rows.
Activated in KSD on KSDK906909.

### 2.4 Untested posting path (severity: note)

Neither class has posted against a real lot yet (task "rebuild, redeploy and
test one lot end to end" is still open; plant 2002 has no 03/04 lots and its
plans are step 4 of PLANT-2002-QM-SETUP.md). The QC-lot class calls the QM
BAPIs locally in the save phase and relies on RAP's commit; the mass class
uses RFC-to-self with its own commit. Both are legal RAP patterns; the first
one to be exercised against a real lot decides whether the other should be
aligned to it.
