Scan Suite Access Control

App-level login, an admin who manages users, and per-person access by company code, plant, and screen — layered on top of the Scan Suite without disturbing what already works.

System KSD · client 500 Package ZSOL_ISCAN 4 tables · 1 Gateway service · 2 entities

Read this part first

One design consequence that shapes everything below.

Security boundary

Your warehouse staff don't have SAP user IDs, so the app reaches SAP under a shared SAP account. The new login identifies which person is using the app — it does not replace SAP's own authentication.

That means a frontend-only check is not real security: anyone who knows the shared SAP credential could call the OData services directly and skip the login screen entirely. So every service method has to verify the session token server-side, not just the app screens. That's built into the design below, and it's the reason Phase 2 exists.

This is the right trade for a warehouse floor — you get per-person accountability and per-person access without buying an SAP licence for every operator. It just has to be enforced in ABAP, not JavaScript.

How it fits together

Two independent layers. Only the second one is new.

Existing

SAP HTTP authentication

The browser authenticates to /sap/opu/odata/… as it does today, under one shared SAP account. Unchanged — nothing in this spec touches it.

New

App login & authorization

A person signs in with their own app username and password. The backend returns a session token plus that person's company codes, plants, and permitted screens. Every later call carries the token; ABAP checks it and filters data accordingly.

Passwords are never stored or transmitted in the clear. Each user gets a random salt, and the table holds only SHA-256(salt + password) as hex. There is no way to read a password back out of the table — a forgotten password is reset by an admin, not recovered.

Table 1 of 4

ZSOL_APP_USER Scan Suite app user master 
@EndUserText.label : 'Scan Suite app user master'
@AbapCatalog.enhancement.category : #NOT_EXTENSIBLE
@AbapCatalog.tableCategory : #TRANSPARENT
@AbapCatalog.deliveryClass : #A
@AbapCatalog.dataMaintenance : #RESTRICTED
define table zsol_app_user {

  key client       : abap.clnt not null;
  key username     : abap.char(20) not null;
      full_name    : abap.char(40);
      pwd_hash     : abap.char(64);
      pwd_salt     : abap.char(32);
      is_admin     : abap.char(1);
      active       : abap.char(1);
      fail_count   : abap.int1;
      locked       : abap.char(1);
      last_login_d : abap.dats;
      last_login_t : abap.tims;
      ernam        : syuname;
      erdat        : erdat;

}
  • username — the app login name. Deliberately not tied to SAP's 12-character user ID, since these people have no SAP account.
  • pwd_hash — 64 hex characters: SHA-256 of salt + password. Never the password itself.
  • pwd_salt — 32 hex characters, generated fresh per user, so two people with the same password still get different hashes.
  • is_admin — X grants access to the admin screen (creating users and assigning access).
  • fail_count / locked — consecutive wrong passwords; the account locks at 5 and only an admin can clear it.

define table zsol_app_uorg {

  key client   : abap.clnt not null;
  key username : abap.char(20) not null;
  key bukrs    : bukrs not null;
  key werks    : werks_d not null;

}
  • One row per company code + plant a person may work in. Someone covering three plants gets three rows.
  • werks = '*' means every plant in that company code — so a company-wide user needs one row, not one per plant.
  • No rows at all means no data access. That's deliberate: a newly created user sees nothing until an admin grants something.

ZSOL_APP_SESS Active login sessions 
@EndUserText.label : 'Scan Suite active login sessions'
@AbapCatalog.enhancement.category : #NOT_EXTENSIBLE
@AbapCatalog.tableCategory : #TRANSPARENT
@AbapCatalog.deliveryClass : #A
@AbapCatalog.dataMaintenance : #RESTRICTED
define table zsol_app_sess {

  key client    : abap.clnt not null;
  key token     : abap.char(32) not null;
      username  : abap.char(20);
      created_d : abap.dats;
      created_t : abap.tims;
      expires_d : abap.dats;
      expires_t : abap.tims;

}
  • A successful login writes one row; the token is a random 32-character value, not derived from the username.
  • Sessions expire after 12 hours — long enough for a full shift, short enough that a mislaid handheld stops working by the next one.
  • Expired rows are cleaned up on the next login by the same user, so the table stays small without a background job.

Gateway service

One new SEGW project, same pattern as ZSOL_LOC_ISCAN.

Create SEGW project ZSOL_APP_AUTH, generate runtime artifacts, and register the service as ZSOL_APP_AUTH_SRV in /IWFND/MAINT_SERVICE. Two entities — every property is Edm.String, so there are no type dropdowns to get wrong.

A person's company codes, plants and screens travel as single delimited string properties rather than nested collections. That's the same shape the Challan service already uses, and it exists for a concrete reason: classic Gateway raises CREATE_DEEP_ENTITY not implemented for generated associations, so a flat scalar property sidesteps the problem entirely.

Entity Login → entity set LoginSet

Set the entity set creatable only — untick updatable, deletable, pageable and addressable. A login is a POST, never a readable collection.

One thing not to skip

Password must never be returned. Leave it out of every response in the data provider — the app has no reason to read one back, and a write-only field is the easiest kind to keep from leaking into a log.

The first admin

Solving the chicken-and-egg problem without typing a hash by hand.

You can't create the first admin through the admin screen, and you can't type a password into SE16 because it has to be salted and hashed first. So I'll write a small report, ZSOL_APP_USER_BOOTSTRAP, that you run once in SE38: it takes a username, a full name and a password on the selection screen, generates the salt, hashes the password, and writes the user with is_admin = 'X' plus full access to every company code, plant and screen.

After that first login, every other user is created from inside the app. Run the report once, then leave it alone — it's a bootstrap tool, not a maintenance one.
