All three apps are already deployed. Nothing in this guide installs software. Every step below is launchpad configuration and role authorization — the BSPs, OData services and CDS objects are live in KSD today and were verified by direct database read.

1. Where things stand

A read of TADIR for R3TR WAPA in client 500 confirms 52 Z-namespace BSP applications exist in KSD. Twenty-five of them correspond to app folders in this repository, and all 25 are deployed — including the three built this week. No deployment work is outstanding.

What is missing is launchpad configuration. Three deployed apps have no tile, and their OData V4 service groups are absent from both KGPL roles, so even a correctly built tile would fail authorization at runtime.

4. Part A — OData V4 authorization

Do this first. A tile without its service group in the role will render and then fail on the first data call.

KSD carries two KGPL roles. Neither contains the three new service groups today — verified by reading AGR_HIERT:

RoleDescriptionV4 groups todayNotes
ZKGPL_ALLKGPL ALL APPS26Carries the catalog assignment for the space. Must be updated.
ZKGPL_BR_PROCUREKEJRIWAL FIORI APPS~30Newer role; carries the five ZKGPL_FIORI apps. Update for parity.

Procedure — repeat for each of the three service groups

  1. Run PFCG, open role ZKGPL_ALL, click Change.
  2. Go to the Menu tab.
  3. Position the cursor on the folder that holds the existing R3TR G4BA entries (the catalog node, object ID 2).
  4. Choose Insert Node → Authorization Default.
  5. In the dialog select object type TADIR Service and enter:
    Program ID: R3TR   Object Type: G4BA   Object Name: ZUI_PROD_CONFIRM_04
  6. Repeat for ZUI_WIP_BATCH_04 and ZUI_LABEL_MASTER_04.
  7. Save the menu.
  8. Go to the Authorizations tab, click Change Authorization Data, accept the merge of new default values, then Generate the profile.
  9. Save the role. Repeat the whole sequence for ZKGPL_BR_PROCURE.
  10. Have each affected user log off and back on, or run PFUD for a user master comparison.
If the merge dialog offers “Read old status and merge with new data”, take it. Choosing “Read new data” discards the manual authorization adjustments already made in these roles.

Verifying Part A

After generation, the three entries should be visible in the role menu. To confirm from the database side, the role menu text table should return three new rows:

SE16N → AGR_HIERT, filter AGR_NAME = ZKGPL_ALL, TEXT = R3TR G4BA ZUI_* — expect 29 rows, up from 26.

5. Part B — semantic objects

The three semantic objects — ProdConfirmation, WipBatch, LabelMaster — are not registered in /UI2/SEMOBJ. Neither are the ones used by the five apps already running in production (PalletStock, DeliveryChallan, ReturnBox, PurchaseRegister, PackingUnit).

Registration is therefore optional — the launchpad accepts an unregistered semantic object with a warning, which is how every existing KGPL tile works today. Registering them removes the warning and makes the intent discoverable in /UI2/FLIA.

  1. Run /n/UI2/SEMOBJ.
  2. Click New Entries.
  3. Add three rows, leaving the component blank: ProdConfirmation, WipBatch, LabelMaster.
  4. Save to a customizing request.

6. Part C — target mapping and tile

Both live in the same business catalog. The role menu entry for this catalog reads X-SAP-UI2-CATALOGPAGE:ZKGPL_BC_CUSTOM, which means the launchpad page is generated from the catalog. There is no separate group to maintain — a tile added to the catalog appears in KGPL CUSTOM APPS automatically.

C1 — create the target mapping

  1. Run /n/UI2/FLPD_CUST.
  2. Select catalog ZKGPL_BC_CUSTOM in the left pane.
  3. Open the Target Mappings tab and click + (Create Target Mapping).
  4. Fill in from the parameter card in section 7: Semantic Object, Action, Application Type = SAPUI5 Fiori App, Title, URL, ID (the component ID).
  5. Under Device Types tick Desktop, Tablet and Phone.
  6. Leave Parameters empty — none of the three apps take startup parameters.
  7. Save.

C2 — create the tile

  1. Still in ZKGPL_BC_CUSTOM, open the Tiles tab and click +.
  2. Choose tile type App Launcher – Static.
  3. Enter Title, Subtitle and Icon from the parameter card.
  4. Leave Information and Keywords blank, or add a keyword to help search.
  5. Under Navigation, set Use semantic object navigation = Yes, then enter the same Semantic Object and Action used in C1.
  6. Save.
The tile and the target mapping are matched only by the semantic object and action strings. A typo in either produces a tile that opens a blank page with “the app could not be opened because the navigation target is not available”. Copy and paste rather than retype.

8. CO03 — Display Production Order

CO03 is step 4 of the plant runbook and has no tile anywhere. It is standard SAP and needs no development. The transaction exists in KSD (SAPLCOKO1, screen 0110).

The reliable route is a SAP GUI transaction tile in the same catalog:

  1. Check for an existing mapping first. Run /n/UI2/FLIA and resolve ProductionOrder-displayFactSheet. The semantic object ProductionOrder is SAP standard (component PP-SFC) and a shipped target mapping may already exist. If one resolves, you only need a tile pointing at it — skip to step 4.
  2. If nothing resolves, create a target mapping in /n/UI2/FLPD_CUST, catalog ZKGPL_BC_CUSTOM, with Semantic Object ProductionOrder and Action displayKejriwal. Use the custom action rather than display so a future SAP mapping on the standard action cannot collide with yours.
  3. Set Application Type = Transaction and Transaction Code = CO03 (verified present in KSD as SAPLCOKO1, screen 0110).
  4. Set System Alias to the alias used by the other GUI tiles in this catalog — blank means the local system, which is correct for an embedded deployment.
  5. Create a static App Launcher tile titled Display Production Order, subtitle Production, icon sap-icon://factory, pointing at whichever semantic object and action resolved in step 1 or was created in step 2.
Before creating this, check the SAP Fiori Apps Library for a native app for your exact release — if one is available it gives a better experience than the GUI-for-HTML fallback. Do not assume an app ID; look it up against the release level of KSD.

9. Cache invalidation

Launchpad content is heavily cached at four layers. Skipping any one of these produces the classic “I saved the tile but it isn't there”.

Transaction / reportWhat it clearsWhen
/n/UI2/INVAL_CACHESGlobal launchpad cachesAfter every catalog change
/n/UI2/CACHE_DELClient-side FLP cacheAfter every catalog change
SE38 → /UI5/APP_INDEX_CALCULATEUI5 app indexAfter a new BSP or component ID appears
/n/IWFND/CACHE_CLEANUPGateway metadata cacheIf $metadata looks stale
/n/IWBEP/CACHE_CLEANUPBackend metadata cacheIf $metadata looks stale
Run /UI5/APP_INDEX_CALCULATE with full calculation selected, not the delta run. The three components are new to the index and a delta run has been observed to miss BSPs in $TMP.

Finally, clear the browser: hard reload, or open the launchpad once with ?sap-ui-xx-componentPreload=off&sap-language=EN appended to force a fresh descriptor read.

Appendix B — the $TMP problem

This is outside the scope of tile creation but it is the largest risk in the landscape, and it is worth deciding on before more tiles are added.

Twenty of the twenty-five repo apps sit in $TMP. Objects in $TMP are local: they cannot be captured in a transport request and therefore cannot reach KSQ or any downstream client. Everything works in KSD and nothing moves.

Seventeen BSPs in ZKGPL_FIORI have no source in version control. They are transportable but unrecoverable — if one is overwritten or deleted there is no copy to restore from.

Together, 37 of the 52 live BSPs are in one of these two states.

Remediation, in the order I would do it

  1. Repoint the 20 $TMP apps to ZKGPL_FIORI. In SE80, open each BSP, choose Change package, assign ZKGPL_FIORI and a workbench request. Alternatively update ui5-deploy.yaml in each app folder and redeploy — slower, but it keeps the repo and the system in agreement.
  2. Download the 17 orphans into apps/. Either pull the BSP sources through abapGit into the existing repository, or export each BSP from SE80. Once they are in git, a redeploy accident is recoverable.
  3. Then and only then, cut a transport to KSQ. Attempting it before step 1 silently drops 20 apps.
The three apps in this guide are themselves in $TMP. The tiles you create will work in KSD, but neither the tiles nor the apps will transport until step 1 is done. If the plan is to go live from KSD directly, that is fine — but it should be a decision rather than an accident.
