Backend is done. The RAP objects, service definition and service binding are active and published, verified by direct read of KSD (TADIR SRVB + G4BA entries for ZUI_QC_INSPECTION_04). This guide covers only what is left: the three UI5 apps and their launchpad tiles.

1. Where things stand

None of the three BSP applications exist in KSD yet — a live search of ZQC_* against the repository information system returned zero results. This is genuinely new deployment work, unlike the earlier three apps (Cancel Production Confirmation, WIP Batch Close, Label Master) which were already live when their FLP guide was written.

Three code-level gaps were found and fixed in this pass, before writing this guide, so the apps are ready to deploy rather than deployed-then-patched:

  • Plant value help. onPlantHelp in all three worklist controllers was a stub (MessageToast.show("Plant value help")), not wired to any control. Replaced with a working SelectDialog over /PlantVH (ZI_VH_PLANT), the same pattern already used in the batch-status app. The Plant input now carries showValueHelp="true" valueHelpRequest=".onPlantVH".
  • Hard-coded operation number. onRecord in all three detail controllers sent a literal "00000010" regardless of what operation the lot's characteristics actually belong to. It now reads OperationNumber off the first bound characteristic row in the lot's own unfiltered characteristics list, which is correct because each of these three apps is scoped to one inspection stage and therefore one operation per lot.
  • Missing UD_SELECTED_SET. BAPI_INSPLOT_SETUSAGEDECISION needs UD_SELECTED_SET in addition to code group and code — the code group alone does not identify a code, because the same group can appear in more than one selected set. This field was added to ZD_QC_USAGE_DECISION earlier, but the UI never actually sent it. It now sends the constant UD_SELECTED_SET = "ZQC_UD". This value has not been confirmed against QS51 customizing — if Usage Decision posting fails with a selected-set error, this is the one constant to correct (see section 9).

4. Part A — deploy the three BSPs

Two ways to do this; use whichever has worked before in this project. Repeat once per app.

Option 1 — command line (fiori deploy)

  1. On a machine with network access to 192.168.0.19:8000 (VPN connected), open a terminal in apps/<app-folder>.
  2. Edit ui5-deploy.yaml and replace <TRANSPORT> with the real transport request number.
  3. Run npm install once per app folder if node_modules is not already present.
  4. Run npm run deploy. This runs fiori deploy --config ui5-deploy.yaml, which builds the app and uploads it as BSP application ZQC_RAW_DYE / ZQC_POST_DYE / ZQC_POST_WIND in package ZKGPL_FIORI.
  5. Confirm in SE80 → BSP Application that the app now exists and contains the expected files.

Option 2 — Eclipse (ADT “Deploy to SAPUI5 ABAP Repository”)

  1. In Eclipse, right-click the app's webapp folder (needs the SAPUI5 Team Provider set up against the ABAP project already used for the RAP work this session).
  2. Team → SAPUI5 → Deploy to SAPUI5 ABAP Repository.
  3. Enter Name ZQC_RAW_DYE (or the matching name per app), Package ZKGPL_FIORI, and the transport request.
  4. Finish, and watch the Console view for a successful upload.
Whichever option is used, keep it the same for all three apps and for any future redeploy — mixing command-line and Eclipse deploys against the same BSP has not caused a problem in this project so far, but there is no reason to test that.

5. Part B — confirm authorization

This part is already done. ZUI_QC_INSPECTION_04's G4BA service group was inserted into role ZKGPL_BR_PROCURE (the role used for all Fiori apps in this project) via PFCG → Menu → Insert Node → Authorization Default → TADIR Service, the profile was regenerated, and the user confirmed completion before this UI work began.

6. Part C — target mapping and tile

Same catalog as every other KGPL app — ZKGPL_BC_CUSTOM, generated as a page automatically, no separate group to maintain.

C1 — create the target mapping (repeat three times)

  1. Run /n/UI2/FLPD_CUST.
  2. Select catalog ZKGPL_BC_CUSTOM in the left pane.
  3. Open the Target Mappings tab and click +.
  4. Fill in from the parameter card in section 7: Semantic Object, Action = inspectKejriwal, Application Type = SAPUI5 Fiori App, Title, URL, ID (component ID).
  5. Under Device Types tick Desktop and Tablet only — the three manifests declare "phone": false, matching how narrow the characteristics lists are to read on a phone screen.
  6. Leave Parameters empty.
  7. Save.

C2 — create the tile (repeat three times)

  1. Still in ZKGPL_BC_CUSTOM, open the Tiles tab and click +.
  2. Choose tile type App Launcher – Static.
  3. Enter Title, Subtitle and Icon from the parameter card.
  4. Under Navigation, set Use semantic object navigation = Yes, then enter the same Semantic Object and Action used in C1.
  5. Save.
The tile and the target mapping are matched only by the semantic object and action strings. Copy and paste rather than retype — a typo produces a tile that opens to “the app could not be opened because the navigation target is not available”.

Confirm UD_SELECTED_SET against QS51. All three apps currently send the constant "ZQC_UD", matching the existing ZQC_UD code group by name. This is a reasonable default, not a verified one — the BAPI will reject it cleanly with an error message if it is wrong, it will not silently misfile a usage decision. The constant lives at the top of each Detail.controller.js, one line to fix in all three files.
Still open from the QM master-data workbook (item 8, unchanged by this pass): the grade code list and the coning-oil target block in QS21. Neither blocks deploying or opening the apps — the worklists and characteristic lists render regardless — but the grade segmented button and some target/tolerance readouts will show as “not maintained” until that customizing is done.
Post-Dyeing recipe qualification and Post-Winding incoming figures both depend on a batch-to-recipe / batch-to-greige-lot link that is not yet confirmed in the data model (also part of item 8). Post-Dyeing defaults to “first of recipe” = true (over-testing, the safe direction). Post-Winding's incoming-figure deltas simply do not render until this is resolved — the absolute values still record correctly.
